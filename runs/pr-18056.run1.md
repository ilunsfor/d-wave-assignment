*Scope, as summarised by the triage model:* This PR adds first-class composite primary key support to Django, introduced via a new virtual field `models.CompositePrimaryKey`, which is set as a model's `pk` and lets a table be created with a multi-column `PRIMARY KEY`. The core logic lives in `django/db/models/fields/composite.py` with supporting changes across model options, base model, queries, SQL compiler, schema backends (base, Oracle, SQLite), serializers, and admin registration (which now refuses composite-PK models). The 5.2 release notes announce the feature, and the new topic guide `docs/topics/composite-primary-key.txt` documents usage and its limitations, including that relations, migrations to or from a composite key, admin registration, and ModelForms are not supported yet.
Four should-fix correctness and API issues touch composite primary key handling. The most consequential is the tuple `IN` subquery rewrite, which can silently compare the wrong columns. These should be addressed, with tests, before merging.

## Should fix

- **`django/db/models/aggregates.py:189-190`**
  ```python
                cols = expr.get_cols()
                return Count(cols[0], filter=result.filter)
  ```
  The replacement `Count` is built from scratch with only `filter`, so the original's explicit `output_field` and other `**extra` kwargs are silently dropped. The new instance is also never passed through `resolve_expression`.
  Suggestion: Copy the resolved instance instead, e.g. `c = result.copy(); c.set_source_expressions([cols[0], result.filter]); return c`. Alternatively, forward the original `extra`/`output_field` and resolve the new object.

- **`django/db/models/fields/composite.py:55-58`**
  ```python
            if kwargs.get("default", NOT_PROVIDED) is not NOT_PROVIDED:
                raise ValueError("CompositePrimaryKey cannot have a default.")
            if kwargs.get("db_default", NOT_PROVIDED) is not NOT_PROVIDED:
                raise ValueError("CompositePrimaryKey cannot have a database default.")
  ```
  `db_column` is accepted but silently ignored, because `get_attname_column` always returns a `None` column. The other meaningless options (`default`, `db_default`) are rejected with an error, so this is inconsistent.
  Suggestion: Add `if kwargs.get("db_column", None) is not None: raise ValueError("CompositePrimaryKey cannot have a db_column.")`, with a test.

- **`django/db/models/fields/composite.py:105-106`**
  ```python
            return ColPairs(alias, self.fields, self.fields, output_field)
  ```
  This affects joins, subqueries and aliased tables. When `alias` differs from the model's table and `output_field` is None, `ColPairs` is built with `output_field=None`. The cached path uses `self` instead, and `Field.get_col` also defaults `output_field` to `self` in this case.
  Suggestion: Add `if output_field is None: output_field = self` before constructing `ColPairs`, mirroring `Field.get_col`.

- **`django/db/models/fields/tuple_lookups.py:311-313`**
  ```python
            if isinstance(lhs, ColPairs):
                rhs = rhs.clone()
                rhs.set_values([source.name for source in lhs.sources])
                lhs = Tuple(lhs)
  ```
  When the LHS is a `ColPairs`, the subquery's select is overwritten with the LHS model's field names, ignoring whatever the user selected on the RHS queryset. If the RHS is a different model or selects differently named columns (e.g. `pk__in=Other.objects.values('x', 'y')`), the subquery either raises `FieldError` or silently compares the wrong columns.
  Suggestion: Only rewrite the RHS select when it is a single `ColPairs` (the `.values('pk')` case), and expand it using the RHS's own `ColPairs` targets rather than the LHS source names. Leave explicitly selected multi-column subqueries untouched. Add tests covering a cross-model subquery.
