*Scope, as summarised by the triage model:* This PR adds composite primary key support to Django via a new virtual field, `models.CompositePrimaryKey(*field_names)`, which is assigned as a model's `pk` to make the underlying table use a multi-column primary key, with values exposed and filterable as tuples. The implementation touches the model base and options (`is_composite_pk`), the new `django/db/models/fields/composite.py`, the query compiler and lookups, schema editor backends (base, SQLite, Oracle), the serializer, and admin registration, which now raises `ImproperlyConfigured` for composite-PK models. The docs (new topic page `composite-primary-key`, `docs/releases/5.2.txt`, and the `fields.txt` reference) describe it as a 5.2 feature with known limitations: no relational fields or GenericForeignKey support, no ModelForm or admin support, and no migration of primary keys to or from composite form.
One should-fix correctness issue needs addressing before merge. The Count rewrite path discards the resolved expression's state and any extra kwargs passed to the original aggregate. It is localized and straightforward to correct.

## Should fix

- **`django/db/models/aggregates.py:189-190`**
  ```python
                  cols = expr.get_cols()
                  return Count(cols[0], filter=result.filter)
  ```
  This returns a brand-new, unresolved `Count` instead of the resolved `result`. Two things are lost:
  - Any state `resolve_expression()` set on the clone, such as `is_summary` or other summarize state.
  - Extra kwargs passed to the original aggregate, such as `output_field` or other `**extra`.

  Suggestion: Mutate the resolved clone instead of constructing a new one, e.g.:
  ```python
  source_expressions = result.get_source_expressions()
  source_expressions[0] = expr.get_cols()[0]
  result.set_source_expressions(source_expressions)
  return result
  ```
