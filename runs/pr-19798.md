# Review: pr-19798

*Tier SMALL · 4 of 4 files reviewed in 1 call · claude-opus-5-5 · 2026-11-07*

*Scope, as summarised by the triage model:* This PR changes `_get_field_expression_map` in `django/db/models/base.py` so that it iterates over all local fields rather than only local concrete ones, and computes values for non-concrete `ForeignObject` relations by gathering the values of their `from_fields` on the instance (as a tuple, or a single value when there is only one). Non-concrete fields that are not foreign-object relations are skipped. The tests in `tests/foreign_object/` (new models in `customers.py` plus additions to `tests.py`) exercise this path. I have not seen release notes or docs text in the PR, so I can't say what the change is intended to be advertised as.
This shouldn't merge yet. Values for a ForeignObject's `from_fields` are read in a way that can return related instances or raise instead of yielding column values. The new exclude tests also pass regardless of whether exclusion works, so they don't cover the behaviour they claim to.

## Should fix

- **`django/db/models/base.py:1375-1377`**
  ```python
                      value = tuple(
                          getattr(self, from_field) for from_field in field.from_fields
                      )
  ```
  `getattr(self, <from_field name>)` returns a related model instance when a from_field is itself a relation such as a ForeignKey, instead of the raw column value. That can trigger a DB query or raise `RelatedObjectDoesNotExist`. The names are also not resolved the way ForeignObject resolves them, e.g. `'self'`.
  Suggestion: Use the resolved local fields and their attnames: `tuple(getattr(self, f.attname) for f in field.local_related_fields)`.

- **`tests/foreign_object/tests.py:797-800`**
  ```python
          @skipUnlessDBFeature("supports_table_check_constraints")
          def test_validate_constraints_excluding_foreign_object_member(self):
              customer_tab = CustomerTab(customer_id=150)
              customer_tab.validate_constraints(exclude={"customer_id"})
  ```
  Both exclude tests use `customer_id=150`, which satisfies the constraint anyway, so they pass whether or not exclusion has any effect. Excluding `customer_id` still validates the constraint through `customer`, because the foreign-object value is built from the excluded field. That behaviour is untested and arguably wrong.
  Suggestion: Use a violating value such as `1500` in the exclude tests and assert the intended outcome. Consider skipping a ForeignObject whose `from_fields` intersect `exclude`.
